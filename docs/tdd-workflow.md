# TDD ワークフロー設計

## 背景

Claude Code を使ったAIコーディングの品質を上げるため、ハーネスエンジニアリング（rules / skills）を活用した TDD ワークフローを設計する。

## 採用方式: 型駆動 + wada式TDD

wada式TDD（Red → Green → Refactor）をベースに、LLM向けのアレンジとして**型設計フェーズ**を前に置く。

```
wada式TDD:         テスト(Red) → 実装(Green) → リファクタ
本方式:     型で制約 → テスト(Red) → 実装(Green)
```

### なぜ型設計を前に置くか

- 人間はテストを書きながら設計を発見できる（TDDの本質）
- LLMはそれが苦手。先に型で制約を与えないと、テストと実装で設計がブレる
- 型がある＝LLMにとっての「設計意図の伝達手段」になる

### リファクタフェーズについて

- rules（typescript.md, design-policy.md）が常時適用されるため、最初からルールに沿ったコードが出る前提
- 必要に応じて `/simplify` か `/refactor`（`rules/refactoring.md` を opt-in で読み込む）で別途リファクタ可能

## ワークフロー（4ステップ）

### Step 1: `/design` — 型・IF設計

- 型定義（type / interface）を作成
- 関数シグネチャをexport（中身は未実装）
- design-policy.md のルール（データ駆動、判定関数、純粋関数等）がガードレールとして機能

### Step 2: `/test-cases` — テストケース設計

- Step 1 の型・IFを入力として、テストケースを日本語で列挙
- `it("〜")` の記述のみ。テストの実装は行わない
- 具体的なインターフェースがあるため、ケースが具体的になる

### Step 3: `/test-impl` — テスト実装

- テストケースにコードを実装
- この時点で全テストが失敗（Red）することを確認
- 失敗するテストが「Claudeのゴール」になる

### Step 4: `/impl` — 本実装

- プロダクションコードを実装
- テスト実行して全テストが通る（Green）ことを確認

## ハーネス構成

### Rules（常時適用）

| ファイル | 役割 |
|---|---|
| `rules/typescript.md` | TypeScript コーディングルール（既存） |
| `rules/design-policy.md` | 設計・実装方針（既存） |
| `rules/vitest.md` | テストのスタイル規約（新規・短く） |

### Skills（オンデマンド）

| スキル | 役割 |
|---|---|
| `/design` | 型・IFの設計。ガワだけexportする |
| `/test-cases` | テストケースを日本語で列挙 |
| `/test-impl` | テストコードを実装。実行してRedを確認 |
| `/impl` | 本実装。テスト実行してGreenを確認 |
| `/refactor` | `rules/refactoring.md` を読み込み、スメル検出とレシピでリファクタ（opt-in） |

### なぜ4つのSkillsに分けるか

1. **各ステップでユーザーがレビュー・修正できる** — LLMが一気にやると途中の設計ミスが最後まで伝播する
2. **コンテキストが明確** — 各Skillが「前のステップの出力を入力として受け取る」構造になり、LLMの出力が安定する
3. **問題の切り分けが容易** — テストが通らないとき、設計が悪いのか実装が悪いのかがステップで分かる

## 検討した他のアプローチ

### アプローチ1（不採用）

```
テストケース(日本語) → 本実装 → テスト実装
```

- IF未定の状態でテストケースを書くため、LLMが「なんとなくの関数像」でケースを作り齟齬が出やすい
- テストが実装の後なので「実装に合わせたテスト」になり検証力が落ちる

### アプローチ2（ベースとして採用、テスト順序を調整）

```
IF洗い出し → ガワ実装 → テストケース(日本語) → 本実装 → テスト実装
```

- IF先行は良いが、テスト実装が最後だと本実装の検証に使えない
- テスト実装を本実装の前に移動して最終方式とした
