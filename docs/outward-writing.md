# 外向けの文書の書き方

外向けの文書とは、リポジトリの外の読み手に届く文書を指す。  
コミットメッセージ、PR / MR のタイトルと本文、コミットされるファイル (文書、コード、コメント)、リリースノート、共有する資料が該当する。  
この指針は、外向けの文書に書かないものと、コミットメッセージと PR / MR の本文の書式を定める。  
機械向けの要約は `.claude/rules/outward-writing.md`。  
用語と表記は `docs/wording-guideline.md` に従う。

外向けの文書は、書いた後に取り消しにくい。  
コミットの履歴と公開した文書は、読み手の手元に残る。  
書く前と、出す前の 2 回、この指針で確認する。

## 1. 判断基準

判断基準は 1 つである。

> このリポジトリだけを見た新規参加者が、追加の文脈なしに理解でき、疑問や混乱が残らないか

残るなら、その記載は外向けに書かないか、単体で読めるように書き換える。

## 2. 書かないもの

| 番号 | 書かないもの | 例 |
|---|---|---|
| 1 | git 管理外のローカルのパスとファイル名 | 作業メモのディレクトリ、個人用の設定ファイル、バックアップの保存先、一時ディレクトリ、個人のマシンの絶対パス |
| 2 | 無関係なリポジトリ名と、個人環境の固有名詞 | 参考にした別のプロジェクトの名前、ローカルのディレクトリ構成 |
| 3 | 内部ラベルと、文脈に依存する参照 | 作業サイクルやフェーズの番号、課題の ID、「前回の調査」「例のメモ」 |
| 4 | 作業の手段の話 | AI のエージェント、セッション、スキルの名前、効率のための設定 |
| 5 | シークレットの値や所在を推測できる情報 | 認証情報の保存先、ローテーション前の認証情報に関する記述 |
| 6 | 出所を前提にした説明 | 「翻訳した」「移植した」(出所を知らない読み手には意味が通じない) |

- 3 の例外: 内部ラベルの索引をリポジトリに同梱し、リポジトリだけで意味が分かるようにした場合は、書いてよい
- 4 の例外: エージェント向けの指示のファイル (CLAUDE.md、AGENTS.md、`.claude/` の rules と skills) は、作業の手段そのものを扱う文書なので、4 を適用しない  
  ただし 1〜3、5、6 は適用する
- 公開リポジトリでは、非公開の組織やプロジェクトを特定できる名前 (プロジェクト名、サービス名、ホスト名、アカウントの識別子、人名) も書かない  
  例は、架空の汎用的なものにする (注文 API、会員の画面)

## 3. 書き方

- 外向けには、結論と根拠だけを、単体で読める形で書く  
  経緯、内部の文脈、参考にした資料は、ローカルのメモに残す
- 参照するときは、リポジトリに実在するものを指す (ファイルのパス、ADR の番号とタイトル、同じリポジトリの Issue や PR / MR の番号)  
  読み手が開けないトラッカーの番号は、内部ラベルとして扱う  
  ADR には、Issue や PR / MR の番号を書かない (`docs/adr-guideline.md`)
- 書き終えたら、対象の文を 2 の表の 1〜6 で走査してから出す

## 4. コミットメッセージ

Conventional Commits の形式で書く。

```
<type>(<scope>): <subject>
```

- type は、feat、fix、docs、refactor、test、chore から選ぶ
- scope には、変更したサービスやパッケージの名前を書く (例: `fix(order-api): 在庫がない商品を注文できる不具合を修正する`)
- subject は日本語でよい  
  100 文字以内にする
- 本文を書くときは、変更の理由を書く  
  2 の表の内容は、本文にも書かない

## 5. PR / MR

タイトルと本文は、2 の表と 3 の書き方に従う。  
本文には、次の欄を設ける。  
必須の欄は、該当がないときも省略せずに「なし」と書く。

| 欄 | 必須 | 書くこと |
|---|---|---|
| 概要 | 必須 | 何を、なぜ変更したか |
| 関連する資料 | 必須 | 設計書、ADR、Issue への参照 |
| 設計からずらした点 | 必須 | 設計書や ADR と異なる実装にした箇所と、その理由 |
| 要判断 | 必須 | レビューする人に判断を求める点<br>選択肢と推奨を付ける |
| 確認した内容 | 必須 | 実行した検査と、手元で確認した操作<br>確認していないものは「未確認」と書く |
| リリースの注意 | 該当するときだけ | マイグレーション、環境変数や設定の追加、デプロイの順序、復元の方法 |

```markdown
## 概要

何を、なぜ変更したか。

## 関連する資料

- 設計書: `docs/order-api-design.md` の「注文の取り消し」
- ADR: ADR 0003 (注文の状態の持ち方)
- Issue: #12

## 設計からずらした点

- なし

## 要判断

- なし

## 確認した内容

- 検証コマンドが通過
- 手元で、発送前の注文を取り消せることを確認
- 未確認: 発送後の注文での表示

## リリースの注意

- 注文の表に列を追加するマイグレーションを、デプロイの前に実行する
```

- 関連する資料は、リポジトリのパスとセクションの名前、ADR の番号とタイトル、同じリポジトリの Issue や PR / MR の番号で指す
- 社内の公開先の URL は、非公開のリポジトリでだけ添えてよい  
  公開リポジトリには書かない
- リリースの注意は、マージの後に手作業が要る変更のときだけ書く  
  該当しないときは、欄ごと省略する

欄を設ける理由は、レビューする人が差分から読み取りにくい情報を、書き手が先に示すためである。  
比べる設計書、設計との違い、未決の判断、確認した範囲が本文にあれば、レビューする人は確認する箇所を特定できる。

## 6. AI のトレーラーを付けない

コミットメッセージにも、PR / MR の本文にも、AI のツールが自動で付ける行を付けない。

- `Co-Authored-By: Claude ...` の形式のトレーラー
- "Generated with Claude Code" の形式のフッター

作業の手段は、2 の表の 4 に該当する。  
コミットの著者は、変更に責任を持つ人と、権利が帰属する組織を示す記録である。  
AI のツールを共著者として記録すると、責任と権利の帰属が曖昧になる。

## 7. プロジェクトで決めること

- scope に使う名前の一覧
- 2 の表の走査に使う検索のパターン (プロジェクトに固有のパスやラベル)
- PR / MR のテンプレートと、追加の欄
