# 設計書の書き方

設計書は、1 つのタイトルが示す責務について、振る舞いの仕様 (何ができるか、状態、エラー、方針と理由) をまとめる文書である。  
この指針は、設計書の構成、セクションの書き方、命名、書く範囲、レビューの方法を定める。  
対象は、名前が `-design.md` で終わる Markdown のファイル。  
機械向けの要約は `.claude/rules/design-doc.md`。  
用語と表記は `docs/wording-guideline.md` に従う。

設計書の目的は、読み手が「どう動くか」と「なぜそうしたか」を 1 つの文書で把握できることにある。  
そのために、読み手の問いごとに書く場所を分け、決定したこと、条件、エラーを 1 つのセクションに混ぜない。

## 1. ADR との境界

ADR は決定の理由を残し、設計書は振る舞いの仕様を示す。  
ADR の書き方は `docs/adr-guideline.md`。

| 観点 | ADR | 設計書 |
|---|---|---|
| 書くこと | 決定、根拠、採らなかった案、影響 | 決定の結果としての振る舞い (操作、状態、エラー) |
| 対象 | 構造に関わり、覆すコストが高い決定 | API、CLI、認証、画面などの 1 つの責務 |
| 変更 | accepted の後は本文を書き換えず、新しい ADR で置き換える | 仕様が変わるたびに更新し、常に現在の仕様を示す |

- 判定の問い: 実現方式を別の方式に置き換えたときに書き換えが必要な文は、設計書に書く  
  置き換えても残る文 (なぜその方式を選んだか) は、ADR に書く
- 設計書の「設計方針」の理由は、ADR などの決定の記録にある根拠の要約である  
  採らなかった案と検討の経緯は、設計書に書かない
- 設計書から ADR を参照するときは、番号とタイトルで指す

## 2. 構成

読み手の問いごとに、書く場所を分ける。

| 読み手の問い | セクション | 形 | 要否 |
|---|---|---|---|
| 何の設計か | タイトルと前書き | 何の設計か、この設計書がまとめる内容、扱わない内容 | 必須 |
| 何を扱うか | 項目の表 | 項目と 1 行の説明の表、項目どうしの関係の図 | 項目が複数あるとき |
| 何に依存しているか | 前提 | 外で決まっていることの、1 行の要約とリンク | 依存があるとき |
| 何を決めたか、なぜか | 設計方針 | 「方針 / 理由」の表 | 必須 |
| どう動くか、何を送ると何が返るか | 仕様のセクション | 設計書の種類ごとに決める | 必須 |
| 使うときに何に注意するか | 運用上の注意 | 箇条書き | あるとき |

前提、設計方針、運用上の注意は、設計書の全体に 1 つ置くか、項目ごとに置く。

仕様のセクションは、設計書の種類ごとに次のとおり。

| 設計書の種類 | 仕様のセクション | 例 |
|---|---|---|
| API | API 一覧、共通仕様、データ項目、項目ごとの「状態と操作」と API ごとの仕様 | 注文 API の設計 |
| CLI | 実行の流れ、コマンドの一覧、出力、エラーの表示と終了コード | 管理 CLI の設計 |
| 認証 | 認証の流れ、有効期限 | 認証の設計 |
| 画面 | 画面の遷移、操作、有効時間と間隔、例外の表示 | 会員の画面の設計 |

## 3. セクションの書き方

### 3.1 項目の表

- 項目ごとに、1 行の説明を書く
- 項目ごとのセクションの冒頭に、同じ説明を重ねて書かない

### 3.2 前提

- 外で決まっていることを、1 項目 1 行の要約と、元の文書へのリンクで書く
- 元の文書の中身を転記しない (元の文書が変わったときに、食い違うため)
- 元の文書がまだないときは、要約だけを書き、文書ができたときにリンクを追加する
- 前置きの文は書かない

### 3.3 設計方針

- 「方針」と「理由」の 2 列の表にする  
  方針は「〜とする」、理由は「〜ため」の形で書く
- 理由は、決定の記録 (ADR など) にあるものだけを書く  
  記録にないときは、理由を推測で書かず、空欄のまま一覧にして、決定した人に確認してから書く
- 書くのは、判断が分かれたもの、後から変更しにくいもの、ほかの部品や運用に影響するものにする
- 仕様のセクションに書けば足りる内容 (個々の値、画面の細部) は書かない  
  仕様のセクションに書いた内容を、設計方針に重ねて書かない

| 方針 | 理由 |
|---|---|
| 注文の取り消しは、発送前だけ受け付けるとする | 発送後の取り消しは、返品の手続きで扱うため |

### 3.4 状態と操作

- 状態を持つ項目にだけ置く
- 状態の表 (状態ごとに、持つ値と、できること) と、操作と状態ごとの結果の表を置く
- 何も変更せずに成功する場合と、エラーになる場合も、表のセルに書く

### 3.5 API ごとの仕様

- 見出しは API 名にし、その下に URI を書く  
  対応する CLI のコマンドがあるときは、コマンドも書く
- リクエスト、処理、レスポンス、エラーの順に書く

| 部分 | 形 |
|---|---|
| リクエスト | 表 (項目 / キー / 場所 / 必須 / 内容)<br>指定する項目がないときは「なし」 |
| 処理 | 番号付きの手順<br>1 行に 1 つの動作を書く |
| レスポンス | HTTP ステータスコードと、内容の 2 行の箇条書き |
| エラー | 表 (HTTP ステータスコード / エラーコード / 条件)<br>その API に固有のエラーがないときは「共通のエラーだけ」 |

- 共通のエラーは共通仕様に書く  
  API ごとのエラーの表に載せる共通のエラーは、その API に固有の条件がある 400 だけにする

### 3.6 データ項目

- API が返すデータの種類ごとに、表 (項目 / キー / 型 / 説明) を 1 つ置く
- API ごとのレスポンスには、種類の名前だけを書く (例: 更新後の注文)
- キーと型は、コードの契約の定義 (スキーマ) を正とする

### 3.7 画面の遷移と例外の表示

- 画面の一覧は、項目の表に書く (画面と、その説明)
- 画面の遷移は、全体の流れの図を 1 つ置く  
  「戻る」の操作と例外の遷移は、区間ごとの図に分けて、通常の遷移と一緒に描く (実線は通常の遷移、点線は「戻る」の操作と例外の遷移)
- 前の画面へ戻る遷移の行き先は、角の丸い箱 (例: 「一覧画面へ戻る」) に分ける  
  戻る矢印が画面の箱を指すと、図の自動レイアウトで起点の画面が上に配置されなくなるため
- 時間の値は、「有効時間と間隔」の表にまとめる
- 例外の表示は、表 (表示 / 表示する条件 / 表示する内容と、その後の動作) にする
- 画面ごとの表示要素の細部、画面に表示する文言、画面が呼ぶ API は書かない

### 3.8 運用上の注意

- いつ使うかが名前から分からない API やコマンドの、使う場面を書く
- エラーになったときの対処を書く

## 4. 命名

- API 一覧は、設計書の冒頭に 1 つだけ置く (項目 / 操作名 / API 名 / URI)
- API 名は「対象 + 操作名 + API」とし、空白を入れない (例: 注文登録API)  
  画面名にも空白を入れない (例: 注文一覧画面)
- 操作名は、HTTP メソッドと対応させる

| 操作名 | HTTP メソッド | 操作の内容 |
|---|---|---|
| 一覧取得 | GET | 条件に合うものをすべて返す |
| 登録 | POST | 新しく作成する |
| 変更 | PATCH | 指定した項目だけを変更する |
| 設定 | PUT | なければ作成し、あれば更新する |
| 削除 | DELETE | 削除する |
| 停止、再開、有効化、再発行 | POST | 状態を変更する |

- 項目にも API にも番号を付けない (途中に追加すると番号がずれ、参照が古くなるため)
- ほかの設計書のセクションは、番号ではなく名前で参照する (例: 認証の設計の「会員のログイン」)

## 5. 書く範囲

- タイトルが示す責務だけを書く  
  周辺の内容が必要なときは、追加せずに別の設計書にする
- 実装の進み具合 (実装済みか、いつ実装するか) は書かない  
  設計書は仕様の文書であり、進み具合の文書ではない
- 未決の点は、決定してから載せる
- ほかの文書が扱う内容は、書かずにリンクする
- 設計書が決めるのは、何ができるか、状態、確認の内容、エラー、方針と理由である  
  キー、型、必須かどうかは、コードの契約の定義が決める

## 6. 文面

用語と表記は `docs/wording-guideline.md` に従う。  
設計書では、次も守る。

- プロジェクトに用語集があるときは、用語集の語に合わせる
- 部品は、コードの名前で書く (例: order-api)
- 表の列名は、名詞にする
- 時間の値は、1 分未満は秒、1 分以上は分で書く (例: 30 秒、5 分。300 秒とは書かない)  
  同じ長さを同じ表記にして、値どうしを比べやすくするため
- 並べる条件や対象が 3 つ以上あるとき、または今後増える見込みがあるときは、文の中に読点で並べずに、「以下の〜」の文と箇条書きに分ける (例: 「注文は、以下の条件で取り消す。」の後に、条件を 1 行に 1 つずつ書く)

## 7. 図

- 図は、Mermaid のコードブロックで書く
- 項目どうしの関係の図は `flowchart TD`、複数の部品がやり取りする流れの図は `sequenceDiagram` にする
- 図だけに情報を置かない  
  図の内容は、本文の手順にも書く (図の中の文字は、文書内の検索に一致しないことがあるため)

## 8. レビュー

書いた本人は文脈を持っているため、文書に書かれていない内容を補って読んでしまう。  
読み手に与える情報を制限すると、文書の不足が見つかる。  
そこで、設計書のレビューは、文脈を持たない読み手によるものと、決定を知っている人によるものに分けて行う。

結果は、どちらのレビューでも、「そのまま修正するもの」と「判断が必要なもの (推奨つき)」に分けて出す。

### 8.1 AI のサブエージェントによるレビュー

文脈を持たない読み手として、AI のサブエージェントに依頼する。  
文脈を持たない人が行ってもよい。

| レビュー | 読み手に与えるもの | 方法 |
|---|---|---|
| 初見の読み手 | 設計書 1 つだけ<br>ほかのファイル、コード、リンク先、結論や背景は与えない | 運用の場面 (導入、機器の入れ替え、誤設定の取り消し、契約の終了など) の手順を、設計書だけを根拠に書かせる<br>手順を書けなかった箇所が、設計の不足である |
| コードとの突き合わせ | 設計書とコード | 食い違いを列挙させる<br>設計書が未実装の操作を含むときは、「未実装であることは指摘しない」と前提を伝える |

### 8.2 決定を知っている人のレビュー

方針と理由が決定の記録と一致するかの確認には文脈が必要なので、決定を知っている人が行う。

| レビュー | 読み手に与えるもの | 方法 |
|---|---|---|
| 決定との整合 | 設計書と決定の記録 (ADR など) | 方針と理由が、決定の記録と一致するかを確認する |

## 9. プロジェクトで決めること

次の内容は、公開先やリポジトリの構成に依存するので、この指針では定めない。  
プロジェクトの規約に書く。

- 設計書の保存先と、公開の方法
- 図の大きさの上限
- 書き方の機械検査 (検査を用意したときは、この指針の変更と同じ変更で検査も更新する)
