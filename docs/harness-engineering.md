# ハーネスエンジニアリング

## ハーネスエンジニアリングとは

ハーネスエンジニアリングは、AI エージェントを安全に、一貫して、効率よく動作させるために、エージェントを取り巻く仕組み (ハーネス) を設計する手法である。

```
Agent = Model + Harness
```

- **Model**: 知能 (LLM 本体)
- **Harness**: その知能を実用的にする仕組みの全体

ハーネスがあることで、LLM は自律的に動作するコーディングエージェントになる。

## 各コンポーネントの使い分け

Claude Code のコンポーネント (CLAUDE.md、Rules、Skills、Hooks、MCP) は、ルールの性質で使い分ける。各コンポーネントの機能と設定の方法は、Claude Code の公式の文書を参照する (製品の更新で変わるので、この文書には書かない)。

```
ルールが:
├─ 全セッションで適用すべき?
│  ├─ 情報として伝える (スタイルガイドなど) -> Rules / CLAUDE.md
│  └─ 確定的に強制すべき -> Hook
│
├─ 必要なときだけ読み込む?
│  ├─ ワークフロー (/deploy など) -> Skill (タスク型)
│  └─ ドメイン知識 -> Skill (参照型)
│
└─ 外部サービスと連携する? -> MCP
```

| コンポーネント | 読み込み | 強制力 | 用途 |
|---|---|---|---|
| Rules | 常時。`paths` を指定したものは、対象のファイルを扱うときだけ | 助言的 | コーディング規約、設計方針 |
| Skills | オンデマンド | 助言的 | ワークフロー、ドメイン知識 |
| Hooks | 自動 | 確定的 | フォーマット、バリデーション、通知 |
| MCP | 常時 | ツール提供 | 外部サービスとの連携 |

## ルールと値の分類 (変更の権限)

ルールと値は、変更を決める主体によって 3 つに分類する。分類ごとに、管理の方法が異なる。

| 分類 | 変更を決める主体 | 例 | 管理の方法 | 正本 |
|---|---|---|---|---|
| 規約 | 人 | 型と lint の規約、シークレットの扱い、データの保護、権限の範囲 | ツールとフックで機械的に検査し、違反を拒否する。人が決定したときだけ変更する | 上の「各コンポーネントの使い分け」、`docs/coding-standards.md` |
| 外部仕様 | 外部のサービスや組織 | 外部 API の仕様、レート制限、エラーコードの意味、料金、提携先の規約、法令で決まる値 | 値は 1 か所に定義し、出典と確認日を外部仕様の一覧に記載する。実行時に照合して、食い違ったときに処理を停止できるときは、そちらを優先する | 各プロジェクトの外部仕様の一覧 |
| 運用値 | 観測の結果 (決められた手順で判断する) | 本番の指標で決める閾値、性能の予算、実験の結果で採否を決める機能 | 判断の基準を、結果を見る前に記録する。その手順でだけ変更し、結果を見てから基準を変更しない | ADR の再評価の条件と `review_by` (`docs/adr-guideline.md`) |

AI が起こしやすい誤りは、分類ごとに次のとおり。

- 規約を変更する: 結果を見てから、基準やルールを緩める。-> フックで拒否し、変更は提案までにとどめる
- 外部仕様を確認せずに使う: 記憶や古い確認の内容で書き、相手の変更に気付かない。-> 記憶で書かせず、出典と確認日を必須にし、実行時の照合で検出する
- 運用値をその場で調整する: 途中の結果を見て値を変更する。-> 基準を先に記録する手順を通す

ツールが既に管理しているもの (lockfile のバージョン、`engines`、browserslist、依存の更新の bot) は規約として扱い、外部仕様の一覧には記載しない。

### 外部仕様の一覧

外部仕様の一覧は、プロジェクトが依存している外部仕様を、1 行 1 件で記録する文書である。相手が仕様を変更したときに、修正する場所をこの一覧から特定する。

- `docs/external-specs/` に置く。相手 (外部のサービスや組織) ごとに 1 ファイルにする (例: `docs/external-specs/payment-api.md`)
- 目次を `docs/external-specs/README.md` に置く。目次には、列の説明と、相手の名前とファイルへのリンクだけを書く。外部仕様の行は重ねて書かない

相手ごとのファイルは、次の列の表にする。

| 列 | 書く内容 |
|---|---|
| 外部仕様 | 何が、どの値であるか |
| 出典 | 公式の文書の名前と節、または実際のレスポンス |
| 確認日 | 出典と照合した日。確認できていないときは「未確認」 |
| 定義している場所 | 値を定義しているファイルと名前。行番号では指さない |

`docs/external-specs/payment-api.md` の例:

| 外部仕様 | 出典 | 確認日 | 定義している場所 |
|---|---|---|---|
| レート制限は 100 リクエスト / 分 | 公式の文書「Rate limits」 | 2026-11-01 | `payment.adapter.ts` の `PAYMENT_RATE_LIMIT` |
| エラーコード `card_declined` は再試行しても成功しない | 公式の文書「Errors」 | 2026-11-01 | `payment.parse.ts` の `RETRYABLE_ERROR_CODES` |
| 返金を受け付けるのは決済から 180 日以内 | 担当者からの口頭の説明 | 未確認 | `refund.ts` の `REFUND_WINDOW_DAYS` |

- 出典と確認日は、相手ごとのファイルにだけ書く。コードには値と、一覧の行を指すコメントを書く (同じ情報を 2 か所に書くと、片方だけが更新されるため)
- 確認できていない外部仕様も載せ、確認日を「未確認」にする。未確認のまま依存している箇所が、一覧で分かる
- 規約、運用値、自分たちで決めた仮の値は載せない

```ts
// 外部仕様: docs/external-specs/payment-api.md「レート制限」
const PAYMENT_RATE_LIMIT = 100;
```

機械向けの要約は `.claude/rules/change-authority.md`。既存のプロジェクトでは、初めて読んだセッションで採用するかを 1 回だけ確認し、回答をそのプロジェクトの CLAUDE.md に記録する。
