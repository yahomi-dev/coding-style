# ADR の書き方と運用

ADR (Architecture Decision Record) は、構造に関わる決定を「何を、なぜ、何を捨てて、何が起きるか」の形で残す短い文書である (Michael Nygard、2011)。この指針は、各リポジトリの `docs/adr/` に置く ADR の書き方と運用を定める。機械向けの要約は `.claude/rules/adr.md`、雛形は `docs/adr-template.md`。

ADR の目的は 2 つある。半年後の自分や新しい参加者が「なぜこうなっているか」を 1 ファイルで把握できること。AI が設計意図から外れたコードを書かないための文脈になること。後者のため、古い ADR を放置すると AI がそれに固執して実害が出る。書くことと同じくらい、棚卸しを重く見る。

## 1. 何を ADR にするか

次の 3 つを満たす決定を ADR にする。

- 後から「なぜ」が問われる
- 覆すコストが高い (作り直し、移行、契約の変更を伴う)
- 複数の案から選んだ

対象の例: サービスの区切りと依存の向き、外部システムの選定 (クラウド、DB、IdP)、データの置き場と保持、認証と認可の方式、運用の方針 (配備、IaC、品質ゲート)、規約の制定と機械強制。

ADR にしないもの:

- 実装の詳細 (関数名、環境変数名、列名、エラーの扱い)。仕様書、コードのコメント、PR の説明に置く
- 移行計画、進捗、タスクの表。計画のファイルやチケットに置く
- チケット、Issue、PR / MR の番号。ADR は番号が無くても読めなければならない
- 反証できない抽象的な原則だけのもの (「シンプルさを優先する」)。判定できない原則は淘汰されずに残り続ける。原則は具体的な決定の Context に置く
- 1 つの機能の仕様

迷ったときの問い: 「決定した実現方式を別の方式に置き換えたとき、この文を書き換える必要があるか」。あるなら、その文は ADR ではなく仕様かコードに属する。

細かい判断は決定ログ (日付と番号を付けたローカルのメモ) に書く。ADR はそこから昇格したものだけにする。決定ログは経緯、ADR は結論と根拠。

## 2. 形式

### 2.1 ファイル

- 置き場所は `docs/adr/`。ファイル名は `NNNN-slug.md` (4 桁の連番 + 英小文字とハイフンの slug)。番号は追加順で、欠番は埋めない
- 一覧は `docs/adr/README.md` に置く (番号、題、status、日付)。status が変わったら一覧も直す
- 題は日本語でよい。決定の内容が分かる名詞句にする (「DB の選定」ではなく「PostgreSQL を直接使う」)

### 2.2 frontmatter

```yaml
---
status: accepted            # proposed | accepted | deprecated | superseded
date: 2026-11-04            # status が最後に変わった日
supersedes: [0005]          # 置き換えた ADR の番号 (無ければ省略)
superseded_by: 0012         # 置き換えられた先 (無ければ省略)
review_by: 2027-05          # 再評価の目安 (任意)
confidence: medium          # high | medium | low (任意)
---
```

`review_by` と `confidence` は任意だが、前提が流動的な決定 (費用、外部サービスの仕様、未計測の性能) には付ける。棚卸しの手がかりになる。

### 2.3 節

題の後に次の節をこの順で置く。節の名前は固定する。

| 節 | 書くこと |
|---|---|
| Context | 決定が必要になった事実。プロジェクトで実際に起きている問題、制約、計測値。前提を列挙し、「この前提が崩れたら再検討する」と書く |
| Decision | 何をするか。能動態で「〜する」。強度を MUST / SHOULD で示す。適用範囲。末尾に「決定しないこと」と、その委譲先 (ファイルや ADR の番号 + 題) |
| Alternatives | 検討した案と採らなかった理由。1 案につき 1〜3 行 |
| Consequences | 良い影響、悪い影響、中立な影響。生じる負債。再評価の条件 (いつ、何が起きたら) |
| 参考 | リポジトリ内の実在物 (ファイル、ADR 番号 + 題) と、外部の一次資料 (URL と確認日) |

Context は中立な事実だけを書く。一般論 (「同じ境界に置くと危ない」) ではなく、このプロジェクトで観測した問題を書く。

Decision は実装の自由度を奪わない粒度にする。名前や環境変数名や例外の扱いまで書くと、実装が変わるたびに ADR を直すことになる。

「決定しないこと」は必ず書く。決めていないことを決めたように読ませない。委譲先はリポジトリに実在するものを名指しする。

### 2.4 書き方の規約

- MUST: ADR 単体で読める。読み手は他の文書や会話の記憶を持たないものとして書く
- MUST: 根拠は一次資料 (計測結果、公式文書、コード) と照合できる形で書く。「打ち合わせで確認した」だけを根拠にしない。確認できないことは未確定として「決定しないこと」に回す
- MUST: 参照は番号と章題で指す (「ADR 0012 (AWS のクラウド構成) の Decision 3 (ポータル層)」)。物理行番号で指さない
- MUST: 内部限定の情報を書かない。ローカルのメモ、個人環境のパス、チケット番号、作業の手段 (エージェントやセッション) は外に出さない
- SHOULD: 5〜10 分で書ける長さ (50〜150 行が目安)。10 分で書けないなら、決定が大きすぎるか、実装の詳細を抱え込んでいる
- SHOULD: 70〜80% の完成度で出し、Accepted の前の点検で埋める。完璧を待つと書かれなくなる
- SHOULD: 日付は `YYYY-MM-DD`。括弧は半角 `()`。矢印は `->`。図は Mermaid か文字

## 3. ステータスと置き換え

```
proposed -> accepted -> deprecated
                     -> superseded (superseded_by: NNNN)
```

- **proposed**: 合意前。実装の前に判断が要るときはこの状態で PR に出す
- **accepted**: 合意済み。未確定事項を残したまま accepted にしない。残るなら「決定しないこと」に書いて委譲する
- **deprecated**: 置き換え先が無く、前提が消えて効力を失った
- **superseded**: 新しい ADR で置き換えた。`superseded_by` に番号を書く

accepted の後に変えてよいのは、frontmatter (`status`、`superseded_by`、`review_by`) と、末尾の「追記」の節だけ。追記は日付付きで事実だけを書く (再評価の結果、前提の変化、置き換え先)。Context、Decision、Alternatives、Consequences の本文は書き換えない。本文を変えたくなったら新しい ADR を書く。

置き換えは双方向に書く。新 ADR の `supersedes` と、旧 ADR の `superseded_by` + `status: superseded`。superseded にするのは決定の全体が置き換わったときだけ。一部の項だけが変わるときは新 ADR にどの項を置き換えるかを書き、旧 ADR は accepted のまま「追記」に「Decision N は ADR NNNN (題) に置き換えた」と書く。残る項が少ないなら、新 ADR に残る項も写して全体を置き換える。旧 ADR の Status に括弧で経緯を書き足す形は取らない (語が揃わず、機械で拾えない)。

## 4. 運用

### 4.1 書く時期と書き手

- 決定を実装する PR / MR に同梱する。実装の前に合意が要るなら proposed で先に出す
- AI にドラフトを書かせてよい。決定と accepted の判断は人が行い、責任を持つ
- 規約の制定 (lint、用語集、構造) も ADR にする。規約の中身はルールのファイルに置き、ADR には「なぜその規約を強制するか」を書く

### 4.2 レビューの観点

PR のレビューで次を見る。AI のレビューにも同じ観点を渡す。

- 単体で読めるか。前提知識を要求していないか
- Context が一般論ではなく観測した事実か。根拠が一次資料と照合できるか
- Decision に実装の詳細が入っていないか。「決定しないこと」と委譲先があるか
- Alternatives が 1 つ以上あり、不採用の理由が書かれているか
- status と一覧、`supersedes` / `superseded_by` の整合
- 内部限定の情報、全角の記号、Unicode の矢印が無いか

### 4.3 棚卸し

四半期に 1 回、または大きな節目 (クラウドの変更、作り直し、リリース) の後に、accepted の ADR を一覧で点検する。

- `review_by` を過ぎたもの
- Context の前提が崩れたもの
- 実態と違うのに accepted のままのもの

該当するものは superseded か deprecated にし、必要なら新 ADR を書く。古い ADR を accepted のまま残すことは、AI にとって誤った指示になる。

### 4.4 読まれる仕組み

- 各リポジトリの CLAUDE.md から `docs/adr/` を指す。「詳細な決定は docs/adr/ を正とする」の 1 行でよい
- 新しい参加者は一覧から読む。疑問が出たらまず ADR を探す
- 機械で検査できる決定 (依存の向き、禁止語、用語の別名) は lint、lock、テストに落とし、ADR からそれを名指しする。検査が落ちたとき、直すべきはコードか ADR かを判断できるようにする

## 5. 雛形

`docs/adr-template.md` を写して使う。節の順と名前は変えない。使わない節は「無し」と書いて残す。
