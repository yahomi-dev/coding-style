# 文書の表記と用語

この指針は、文書に使う用語と表記を定める。  
対象は、返答、コミットメッセージ、PR / MR、設計書、ADR、コードのコメント、図のラベルのすべてである。  
機械向けの要約は `.claude/rules/wording.md`。

目的は、読み手が意味を理解するための手間を減らすことにある。  
書き手の独自の言い換えは、読み手に解釈を要求し、機械翻訳でも誤訳されやすい。  
技術者が通常使う用語で書けば、読み手は用語の解釈ではなく内容に集中できる。

## 1. 用語

### 1.1 判定の問い

用語に迷ったら、次の問いで判定する。

> その分野の技術者が、自分で書くときに使う呼び名か

- 技術者が通常使う漢語とカタカナ語で書く (確認する、削除する、スクリプト)
- 和語の言い換え、漢字 1 字の造語、比喩の動詞は使わない
- 同じリポジトリや過去の文書で繰り返し使われていることは、使ってよい根拠にならない  
  過去の文書の語を、新しく書く文に持ち込まない
- プロジェクトに用語集があるときは、用語集の語を優先する

### 1.2 言い換えの表

左の語を使わず、右の語で書く。  
括弧の中は、その意味で使う場合の例。

| 使わない | 使う |
|---|---|
| 組 (会員と商品の組) | 組み合わせ |
| 確かめる | 確認する |
| 消す | 削除する |
| 直す | 修正する |
| 足す | 追加する |
| 作る | 作成する |
| 戻す (データを戻す) | 復元する |
| 置き場所 | 保存先 |
| 鍵 (ストレージの鍵) | 認証情報 |
| 普段どおり | 通常どおり |
| 効く | 機能する、適用される |
| 崩れ | レイアウト崩れ |
| 写し | コピー |
| 決まり、規則 | ルール |
| 台本 | スクリプト |
| 見張る | 監視する |
| 手 (手は 2 つある) | 方法、選択肢 |
| 見立て | 推測、見解 |
| 受け持つ | 担当する |
| 建てる (環境を建てる) | 構築する |
| 流す (コマンドを流す) | 実行する |
| 印、段、版、題 | 属性、ステップ、バージョン、タイトル |

「規約」と「ルール」は、次のように使い分ける。

- 規約: ルールをまとめた全体の名前に使う (コーディング規約、文書作成の規約、プロジェクトの規約)
- ルール: 規約を構成する個々の項目に使う (lint のルール、改行のルール)

表にない語も、1.1 の問いで判定する。

### 1.3 「引く」を意味ごとに分ける

「引く」「引き当てる」を、値の取得や計算の意味で使わない。  
「時間を引く」は引き算と読め、「行を引く」は読み手を選ぶ隠語である。  
意味ごとに次の語に分ける。

| 意味 | 使う | 例 |
|---|---|---|
| 量や結果を出す | 求める、算出する、計算する | 利用時間は、開始時刻と終了時刻から求める |
| 行や値を得る | 取得する、参照する | 注文の行から会員 ID を取得する |
| キーで 1 件に絞る | 特定する | 会員 ID で会員の行を特定する |
| 条件で複数を取り出す | 抽出する | 未発送の注文を抽出する |

### 1.4 API や CLI の仕様を書くときの語

API や CLI の振る舞いを説明するときは、次の語にそろえる。

| 使わない | 使う |
|---|---|
| 状態コード | HTTP ステータスコード |
| 失敗、失敗の種類 | エラー、エラーコード |
| 要求、応答 | リクエスト、レスポンス |
| 弾く | 受け付けない、エラーとする、拒否する |
| 渡す (値を API に送る意味の場合) | 指定する |
| 外す、解除する (設定をなくす意味の場合) | 削除する |
| 置き換える、差し替える | 更新する |
| 保持する (DB に書く意味の場合) | 保存する |
| 検証する (値が条件に合うかを調べる意味の場合) | 確認する (署名やトークンには「検証する」を使う) |

### 1.5 図のラベル

- 関係のラベルは短い動詞にする (指す、持つ、受ける)
- 名詞句の説明をラベルにしない (「利用時間の元」ではなく「指す」)
- 参照の関係は、本文と同じ「〜を指す」にする

### 1.6 例外

- 引用 (エラーメッセージ、ログ、コードの識別子) は、そのまま書く
- 相手の文面にある語は、その文面に合わせるときはそのまま使う
- 既存の文書の語を一括で置き換える変更は、依頼を受けてから、別の変更として行う

## 2. 表記

| 対象 | 書き方 | 例 |
|---|---|---|
| 括弧 | 半角の `()`<br>全角の括弧は使わない | 注文 API (管理者用) |
| 矢印 | `->` `<-`<br>Unicode の矢印は使わない | 登録 -> 確認 -> 完了 |
| 日付 | `YYYY-MM-DD` | 2026-11-04 |
| 時刻 | JST で書く<br>タイムゾーンが文脈から分からないときは `JST` を付ける | 2026-11-04 15:30 JST |
| 英数字と日本語の間 | 半角スペースを入れる | 注文 API で行う |

- 全角の括弧と Unicode の矢印は、検索や置換で一致しない原因になる  
  新しく書く文と編集する箇所は、半角の括弧と ASCII の矢印に統一する
- ログやツールの出力が UTC のときは、JST に換算して書く  
  出力を引用するときは、そのまま書いてタイムゾーンを添える
- 英数字と日本語の間の空白は、既存の文書が空白を入れない表記で統一されているときは、そちらに合わせる  
  1 つの文書の中で表記を混ぜないため  
  表記をそろえ直す変更は、1.6 と同じく、依頼を受けてから別の変更として行う

## 3. 改行

Markdown の文書は、文の区切りで改行する。  
差分が文の単位になり、表示でも文ごとに改行される。

| 場所 | 書き方 |
|---|---|
| 段落 | 1 文を 1 行に書く<br>同じ段落の中で文が続くときは、行末に半角スペースを 2 つ付ける<br>話題が変わったら、空行を入れて段落を分ける |
| 表のセル | 句点を書かない<br>文の区切りは `<br>` にする |
| 箇条書きと番号付きの手順 | 句点を書かない<br>文の区切りは、行末の半角スペース 2 つと、次の行の字下げにする |

- 行末の半角スペース 2 つは、Markdown の改行の書き方である  
  付けないと、次の行とつながって表示される
- 括弧、かぎ括弧、インラインコードの中の句点では改行しない
- コードブロックと frontmatter には適用しない
- コミットメッセージ、PR / MR の本文、コードのコメントには適用しない (行末の空白が保存されない場所があるため)
- 整形と検査は `scripts/markdown` が行う (`pnpm md:format`、`pnpm md:check`)

## 4. 適用

- 書く前に、1.1 の問いと 1.2〜1.4 の表で確認する
- 書いた後に、表の「使わない」の語、全角の括弧、Unicode の矢印が残っていないかを走査する
- レビューでも同じ観点で確認する  
  AI のレビューにも同じ観点を指示する

## 5. プロジェクトで決めること

- ドメインの用語 (用語集)  
  この指針の表よりも用語集を優先する
- ドメインに固有の言い換え  
  プロジェクトの規約に追加する
