# 設計書のルール (機械向けの要約)

正本は coding-style リポジトリの `docs/design-doc-guideline.md`。ここは設計書 (`*-design.md`) を触るときに守る要点だけ。用語と表記は `wording.md` に従う。プロジェクトに設計書の規約があるときは、そちらも守る。

## ADR との境界

- ADR は決定の理由 (根拠、採らなかった案、影響)、設計書は振る舞いの仕様 (操作、状態、エラー)
- 実現方式を置き換えたときに書き換えが必要な文は設計書に、置き換えても残る文は ADR に書く
- 採らなかった案と検討の経緯は、設計書に書かない

## 構成

- 読み手の問いごとに節を分ける: タイトルと前書き -> 項目の表 -> 前提 -> 設計方針 -> 仕様の節 -> 運用上の注意。前提、設計方針、運用上の注意は、全体に 1 つ置くか、項目ごとに置く
- 前書きには、何の設計か、まとめる内容、扱わない内容を書く
- 項目の説明は冒頭の項目の表に 1 行で書き、項目ごとの節の冒頭に重ねない
- 前提は、1 項目 1 行の要約と元の文書へのリンクだけ。中身を転記しない。前置きの文は書かない
- 設計方針は「方針 / 理由」の表 (方針は「〜とする」、理由は「〜ため」)。理由は決定の記録 (ADR など) にあるものだけを書く。記録にないときは推測で書かず、空欄のまま一覧にして確認する
- 設計方針に書くのは、判断が分かれたもの、後から変更しにくいもの、ほかの部品や運用に影響するものだけ。仕様の節に書けば足りる内容 (個々の値、画面の細部) は書かない

## 仕様の節 (設計書の種類ごと)

- API: API 一覧、共通仕様、データ項目、項目ごとの「状態と操作」、API ごとの仕様 (リクエスト / 処理 / レスポンス / エラー の順)
- CLI: 実行の流れ、コマンドの一覧、出力、エラーの表示と終了コード
- 認証: 認証の流れ、有効期限
- 画面: 画面の遷移 (全体の流れの図 1 つと、「戻る」と例外を点線で追加した区間ごとの図)、操作、有効時間と間隔、例外の表示。表示要素の細部、文言、画面が呼ぶ API は書かない
- 状態と操作の表には、何も変更せずに成功する場合と、エラーになる場合も書く
- キー、型、必須かどうかは、コードの契約の定義 (スキーマ) を正とする

## 命名

- API 名は「対象 + 操作名 + API」で、空白を入れない (例: 注文登録API)。画面名にも空白を入れない
- 操作名は HTTP メソッドと対応させる: 一覧取得 GET、登録 POST、変更 PATCH、設定 PUT、削除 DELETE、停止・再開・有効化・再発行 POST
- 項目にも API にも番号を付けない。ほかの設計書の節は、番号ではなく名前で参照する

## 書く範囲

- タイトルが示す責務だけを書く。周辺の内容が必要なときは、追加せずに別の設計書を提案する
- 実装の進み具合 (実装済みか、いつ実装するか) は書かない。未決の点は、決定してから載せる
- ほかの文書が扱う内容は、書かずにリンクする

## 文面と図

- 時間の値は、1 分未満は秒、1 分以上は分 (30 秒、5 分。300 秒とは書かない)
- 並べる条件や対象が 3 つ以上か、今後増える見込みがあるときは、「以下の〜」の文と箇条書きに分ける
- 部品はコードの名前で書く。表の列名は名詞にする
- 図は Mermaid。図だけに情報を置かず、本文の手順にも書く

## レビュー

- AI のサブエージェントによるレビュー (文脈を持たない読み手として行う。文脈を持たない人でもよい): 初見の読み手 (設計書 1 つだけを与え、運用の場面の手順を書かせる。結論や背景は与えない) / コードとの突き合わせ (未実装の操作は指摘しない前提を伝える)
- 決定を知っている人のレビュー: 決定との整合 (方針と理由が ADR などの決定の記録と一致するかを確認する)
- 結果は「そのまま修正するもの」と「判断が必要なもの (推奨つき)」に分ける
