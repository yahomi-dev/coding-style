# ルールと値の分類 (変更の権限)

正本 (表、理由、誤りの例) は coding-style リポの `docs/harness-engineering.md` の「ルールと値の分類 (変更の権限)」。ここは機械向けの要約。

## 採用の確認 (最初に読む)

- 新しく作成するプロジェクトでは、確認せずに採用する
- 既存のプロジェクト (このセッションより前のコミットがある) では、このファイルを初めて読んだセッションで、作業に入る前にユーザーに 1 回だけ確認する: 採用する / 一部だけ採用する / 採用しない
- 回答は、そのプロジェクトの CLAUDE.md に 1 行で記録する (例: `- 規約「ルールと値の分類 (変更の権限)」(coding-style): 採用 (YYYY-MM-DD)`)。一部だけなら、採用する項目を書く。この行があれば、以後は確認しない
- 回答が出るまでと、採用しないプロジェクトでは、下の節を適用しない

## 3 つの分類

ルールや値を追加・変更するときは、変更を決める主体によって、配置と管理の方法を決める。

- **規約** (人が決める。規約、データの保護、権限の範囲、テストの期待値): ツールかフックで拒否する。結果に合わせて緩めない。変更したいときは提案までにとどめる
- **外部仕様** (外部のサービスや組織が決める。外部 API の仕様・レート制限・エラーコードの意味・料金、提携先の規約、法令で決まる値): 下の「外部仕様」に従う
- **運用値** (観測の結果で決める。本番の指標で決める閾値、性能の予算、実験で決める採否): 判断の基準を結果を見る前に記録し、その手順を通してだけ変更する

## 外部仕様

- 外部 API の仕様・レート制限・エラーコードの意味・料金などの外部仕様は、記憶で書かない。公式の文書か実際のレスポンスで確認する
- 値はコードに分散させず、名前の付いた 1 か所 (定数か設定) に定義し、出典と確認日を添える
- 新しく外部仕様に依存したら、プロジェクトの前提の台帳 (例: `docs/assumptions.md`) に 1 行追加する
- 実行時に照合して、食い違ったときに起動しない・処理を停止する形にできるなら、注記よりそちらを選ぶ
- ツールが既に管理しているもの (lockfile のバージョン、`engines`、browserslist、依存の更新の bot) は台帳に記載しない
