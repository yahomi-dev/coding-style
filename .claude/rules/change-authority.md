# 何がそれを変えてよいか

正本 (表・理由・失敗の例) は coding-style リポの `docs/harness-engineering.md` の「何がそれを変えてよいかで分ける」。ここは機械向けの要約。

## 採用の確かめ (最初に読む)

- 新しく作るプロジェクトでは、確かめずに採用する
- 既存のプロジェクト (このセッションより前のコミットがある) では、このファイルを初めて読んだセッションで、作業に入る前にユーザーに 1 回だけ確かめる: 採用する / 一部だけ採用する / 採用しない
- 答えは、そのプロジェクトの CLAUDE.md に 1 行で書く (例: `- 規約「何がそれを変えてよいか」(coding-style): 採用 (YYYY-MM-DD)`)。一部だけなら、採る項目を書く。この行があれば、以後は確かめない
- 答えが出るまでと、採用しないプロジェクトでは、下の節を適用しない

## 3 つの層

ルールや値を足す・変えるときは、何がそれを変えてよいかで置き場所と守り方を決める。

- **人の決定だけ** (規約、データの保護、権限の範囲、テストの期待値): ツールかフックで止める。結果に合わせて緩めない。変えたいときは提案して止まる
- **外の世界** (外部 API の仕様・レート制限・エラーの意味・料金、提携先の規約、法令で決まる値): 下の「外の世界の事実」に従う
- **観測した結果** (本番の指標で決める閾値、性能の予算、実験で決める採否): 判断の基準を結果を見る前に書いて固定し、その手順を通してだけ変える

## 外の世界の事実

- 外部 API の仕様・レート制限・エラーの意味・料金などの外の事実は、記憶で書かない。公式の文書か実際の応答で確かめる
- 値はコードに散らさず、名前の付いた 1 か所 (定数か設定) に置き、出どころと確認日を添える
- 新しく外の事実に頼ったら、プロジェクトの前提の台帳 (例: `docs/assumptions.md`) に 1 行足す
- 実行時に照合して、食い違えば起動しない・処理を止める形にできるなら、注記よりそちらを選ぶ
- ツールが既に追っているもの (lockfile の版、`engines`、browserslist、依存の更新の bot) は台帳に載せない
